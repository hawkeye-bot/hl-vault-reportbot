# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Telegram bot that monitors a single Hyperliquid vault and a specific depositor's position in it, polling the Hyperliquid API and pushing formatted updates (fills, liquidation warnings, sell-coverage mismatches, on-demand `/status`) to a Telegram chat. `/account` is the one exception to the vault-scoped focus: it reports the depositor's whole Hyperliquid account (spot + perp + every vault they're in), not just their stake in this one vault.

## Running

```bash
python -m venv .venv && source .venv/bin/activate   # first time
pip install -r requirements.txt
cp .env.example .env   # then fill in real values
python main.py
```

There are no tests, linter, or build step configured in this repo.

In production this runs as the systemd unit in `deploy/hl-vault-reportbot.service` (installed at `/etc/systemd/system/`). After editing that file, reinstall with `sudo cp deploy/hl-vault-reportbot.service /etc/systemd/system/ && sudo systemctl daemon-reload && sudo systemctl restart hl-vault-reportbot`. Code changes also require a `systemctl restart` to take effect - there's no auto-reload.

## Configuration

All config is env vars loaded via `.env` (see `.env.example`), read once in `src/config.py`:

- `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` — bot credentials and destination chat.
- `VAULT_ADDRESS` — the Hyperliquid vault being watched.
- `USER_ADDRESS` — the depositor whose share of the vault is reported (equity, scaled PnL).
- `POLL_INTERVAL_SECONDS`, `LIQUIDATION_WARN_THRESHOLD`, `HEARTBEAT_INTERVAL_SECONDS`, `HEARTBEAT_FAST_INTERVAL_SECONDS` — tunables, all with defaults.

Quiet hours (23:00–06:00 local time, hardcoded in `src/notifier.py`) hold sends by default. Liquidation warnings, sell-coverage-mismatch alerts, and fill notifications (buy/sell order filled, with or without a chart) all pass `force=True` to bypass this - a fill is something the user wants to know about as it happens, not batched until morning. The heartbeat is the one message still held during quiet hours, by design (it's just a liveness check, not something urgent). The `/status` command replies directly via `update.message.reply_text` rather than through the notifier, so it's unaffected either way.

## Architecture

Five modules, each with one job:

- **`src/hl_client.py`** — `HyperliquidClient` wraps the `hyperliquid` SDK's `Info` endpoint (mainnet, no websocket). All reads (margin summary, positions, fills, open orders, vault details, candles) go through here.
- **`src/state_tracker.py`** — pure functions and the `VaultState` dataclass. No I/O. This is where almost all logic lives: fill grouping, sell-coverage-gap detection, and every `format_*` function that turns raw API dicts into the monospace `<pre>` tables sent to Telegram. Edit here for message-content changes.
- **`src/chart.py`** — `render_candles` turns raw candle dicts into a dark-themed candlestick+volume PNG (`matplotlib`/`mplfinance`, `Agg` backend so no display is needed).
- **`src/notifier.py`** — thin wrapper around `telegram.Bot.send_message`/`send_photo`, tracks `last_sent_at` (used by the heartbeat check) and enforces quiet hours unless the caller passes `force=True`.
- **`main.py`** — wires the above together: `run()` builds the client/notifier/state and a `python-telegram-bot` `Application` (for the `/status` command handler), then runs `poll_loop()` forever alongside it.

### Poll loop (`main.py:poll_loop`)

Runs every `POLL_INTERVAL_SECONDS` and, per cycle:

1. Checks margin ratio against `LIQUIDATION_WARN_THRESHOLD`, sends a one-shot warning (latched by `state.liquidation_warned` until margin recovers).
2. Fetches fills since the last-seen timestamp, dedupes against `state.seen_fill_hashes`, groups partial fills of the same order (`group_fills_by_order`) into a single message.
3. Checks for a long position whose resting sell orders don't cover its full size (`find_sell_coverage_gap`) — skipped for a cycle in which any fill just happened, since the trading bot needs a moment to resize orders and the positions/orders endpoints can be transiently out of sync. Only warns once the gap has been seen on `SELL_COVERAGE_GAP_STREAK_THRESHOLD` (3) consecutive cycles (`state.sell_coverage_gap_streak`), since it's often resolved by the next cycle on its own; any cycle without the gap resets the streak. Latched similarly to the liquidation warning.
4. Sends a heartbeat status message if nothing has been sent in `HEARTBEAT_INTERVAL_SECONDS` — or in `HEARTBEAT_FAST_INTERVAL_SECONDS` if any coin currently has exactly one resting buy order (`has_single_buy_order_left`), signaling its DCA ladder is down to its last rung and worth watching more closely.

### "Distance" and first-entry-price tracking

Buy-side "Distance" is measured from the price of the fill that *originally opened* the position from flat — not the blended average entry price, which shifts with every DCA buy. This price is tracked in `state.first_entry_price[coin]`:

- Seeded at startup from fill history (`find_position_open_price`, 30-day lookback via `FIRST_ENTRY_LOOKBACK_MS`) so it's correct even if the bot was offline when the position opened.
- Updated live whenever a fill opens a position from flat (`startPosition == 0`).
- Cleared when a position returns to flat.

Sell fills omit "Distance" (and the fill count) entirely — `format_fill` instead reports either a full close (plus resulting equity) or the exposure remaining on a partial sell. Every fill message is prefixed with a bold "Buy order filled" / "Sell order filled" header so the type reads unambiguously even in a notification preview.

### Open-order numbering

`format_open_orders` only lists buy orders (the DCA ladder) - sell orders are shown in `format_position_status`'s "Sell price" row instead, not repeated here. Its "#" column numbers each coin's resting buy orders 1 (closest to market, next to fill) through N (deepest); reduce-only orders aren't numbered. Two problems had to be solved together, both in `assign_order_numbers`:

- **Numbers must survive fills.** They're assigned once (the first time a set of oids is seen) and then frozen in `state.order_numbers`, keyed by oid - not recomputed by position every cycle - since fills always remove the nearest-to-market (lowest-numbered) order first, and a plain re-sort would renumber every survivor each time that happens.
- **The nearest-to-market rung can fill before the bot ever sees it** (e.g. right after a restart), so a fresh assignment can't just start counting from 1 at whatever's currently open - it would then be permanently off by however many rungs already filled unseen. `assign_order_numbers` instead calibrates against `historical_order_sizes` (fill history since the position last opened from flat) to reconstruct the full rung sequence - the fill that first opened the position counts as #1, and every rung since (filled-and-gone or still open) gets the next number - so only currently-open orders end up displayed, but numbered as if every earlier rung were still visible. Real order sizes showed why this can't just use a stored count of past fills: a DCA ladder's size scales by a consistent multiplier per rung (~2.3x observed, estimated via median ratio to stay robust to one outlier pair), so a rung's absolute position is recoverable from its own size against that pattern - except the deepest rung, which is typically capped to whatever capital remains rather than continuing the multiplier, so it's simply given the number after the previous rung rather than fitted to the formula. The opening fill itself rarely fits that multiplier pattern (its ratio to itself is trivially 1), so each level is floored at "previous level + 1" - otherwise the rung right after the entry could round down onto the same number as the entry instead of following it.

Fetching fill history is only worth its cost when something is actually unnumbered (`needs_fresh_numbering`), so `_update_order_numbers` (`main.py`) gates the lookback fetch behind that check rather than doing it every poll cycle. Because the assignment is calibrated from real fill history rather than derived from whatever's currently open, it's also correct again immediately after a bot restart - unlike a naive "renumber from 1" fallback would be.

`format_open_orders` isn't filtered to coins with an open position - it lists every resting buy order in whatever `orders` it's given, which includes a coin sitting flat: the trading bot places a fresh re-entry order within seconds of a position closing (confirmed by cross-referencing `historical_orders` against fill-derived flat windows - a coin with no position essentially always has exactly one resting order trying to reopen it), and that order is real and worth showing. But `historical_order_sizes` can't tell "flat now, about to start a new cycle" from "still mid-cycle" from fill data alone - both just look like fills since the last startPosition==0 fill - so `_update_order_numbers` cross-checks against live `positions` and forces empty history for any coin with no open position, rather than letting a brand-new re-entry order inherit the numbering of the *previous*, already-closed cycle (e.g. #8 instead of #1). The table itself stays a single ungrouped list with no coin column: this vault only ever has orders for one coin at a time (either a full ladder for an open position, or, while flat, at most one pending re-entry order), so nothing in it needs disambiguating. That coin still needs to be named somewhere, though, so `format_position_status` takes a `pending_entry_coin` param (`main.py`'s `_pending_entry_coin` - the coin of any resting buy order that isn't for a currently-open position) and fills its otherwise-blank Symbol row with it whenever there's no open position but a re-entry order is resting.

A filled order is already gone from `orders` by the time a fill shows up, so `_update_order_numbers` (which only keeps numbers for currently-open oids) would have already dropped it before the fill gets processed. `main.py`'s poll loop snapshots `state.order_numbers` into `prior_order_numbers` *before* calling `_update_order_numbers` each cycle, so a buy fill message can still look up which rung just filled and show it in the Symbol row (`format_fill`'s `order_number` param) - e.g. "CRVUSDC Buy #4".

A buy fill message also gets the same "Open orders" table shown in `/status`/heartbeat appended below it (after the "Since unstuck began" table, if that's present too) - `main.py`'s poll loop already has that cycle's post-fill `orders` on hand, so it's the ladder as it stands right after this rung filled, not a stale pre-fill snapshot. Sell fills don't get this - the ladder isn't what a sell is about.

`format_position_status` also takes `sell_price_by_coin` (built by `main.py`'s `_sell_price_by_coin`, the nearest-to-market resting sell price per coin) and shows it as "Sell price", ordered highest-to-lowest price: Sell price, Current price, Entry price.

Every `format_position_status` table (including the flat fallback) leads with "Total vault equity" - `vault_value` itself, the whole vault's total value pooling every follower's capital, distinct from "Equity" right below it (this depositor's own scaled share) and from `/account`'s same-named "Vault equity" row (also this depositor's share, just fetched a different way - see `_user_equity`). It repeats in each per-coin table the same way "Equity" already does whenever there's more than one open position at once, rather than being hoisted out as a one-time header.

### Loss-realizing sell detection

This vault runs [passivbot](https://github.com/enarjord/passivbot), whose ordinary closes only ever trigger above a profit threshold - so any sell fill with negative `closedPnl` is never a normal take-profit; it's most likely passivbot's auto-unstuck mechanism cutting an over-extended position. `format_fill` flags this in the header ("Sell order filled (loss)" vs the normal "Sell order filled").

For context on *why* it happened, `main.py`'s `_update_single_buy_order_tracking` maintains `state.single_buy_order_since` (per coin, when its buy ladder first dropped to exactly one resting order - `buy_order_counts`/`has_single_buy_order_left`'s underlying data). When a loss-realizing sell fill comes in, the poll loop looks up how long that coin had been sitting at one order left and passes it to `format_fill` as `stuck_hours`, shown as a "Stuck" row: a buy ladder that grows through several rungs, then stalls for hours with no further fills, then takes a loss on the next sell - matches the on-chain fingerprint of auto-unstuck triggering on a position whose grid ran out of room. Investigated by reconstructing full position lifecycles from `user_fills_by_time` (paginated past its 2000-record-per-call cap) and cross-referencing passivbot's `docs/config.bot.md`.

`state.unstuck_episode_fills` (per coin, a list of raw fill groups) starts recording once `is_loss_realizing_sell` first fires for that coin, and every subsequent fill for it (either side) gets appended - not just further losses, since the point is to show how the episode resolves (typically one more sell that closes the remainder, often back at a profit). Once there are 2+ entries, the fill message gets a second table appended via `format_unstuck_episode`: Time/Side/Price/Size/PnL for the whole episode so far. The record is cleared when the position returns to flat, same lifecycle as `first_entry_price`.

### Charts

Every fill message - buy or sell - is sent as a photo (`notifier.send_photo`) with the usual table as its caption, rather than as plain text: `main.py`'s `_render_chart` fetches `CHART_LOOKBACK_MS` (12h) of `CHART_INTERVAL` (15m) candles via `client.get_candles` and renders them with `render_candles`. A sell fill's chart still shows the position's earlier buy fills from the same cycle, so it reads as that trade's whole buy-and-sell history, not just the exit in isolation - not general market commentary. Chart fetch/render is wrapped in try/except and falls back to a plain `notifier.send` on failure, so a candle-API hiccup or render error doesn't drop the fill notification.

`_render_chart` also overlays the ladder context onto the chart itself: recent fills (from a fresh `client.get_fills_since` scoped to the chart's own lookback window, so only fills actually visible on it are marked, then further scoped via `fills_since_position_opened` to the fills since the position was last opened from flat - a coin can close and reopen more than once within a 12h lookback window, so without this a chart could mark fills from an already-closed earlier cycle as if they belonged to the position that's actually still open) as triangles: buy fills as red upside-down triangles above each fill's candle (not at the exact fill price - reads as a "bought here" flag pointing down at the candle rather than sitting inside it), sell fills as green right-side-up triangles below each fill's candle - a mirror image (opposite side, opposite point direction, opposite color) so entries and exits are both visible without overlapping. One triangle per resting order that filled, not per partial fill of it - `chart.py`'s `_fill_markers` (shared by both sides) dedupes by `oid` (keeping one representative per order) before plotting, so an order filled across several partials still shows as a single triangle; two-plus *different* orders filling in the same candle stack their triangles outward (upward for buys, downward for sells) instead of overwriting each other, via a separate `addplot` scatter series per stack level. Each resting buy order gets a dashed red line labeled with its rung number (`state.order_numbers`, so it matches `format_open_orders`'s "#" column); resting sell order(s) get a dashed green line labeled "TP"; the last candle's close always gets a dotted orange "Now" line (`_CURRENT_PRICE_COLOR`); the position's blended average entry (`entry_price`, from the same `_entry_price_by_coin` used elsewhere, but treated as absent rather than $0 - a sell that just closed the position out can leave a stale zero-size `entryPx` behind) gets a dotted blue "Entry" line (`_ENTRY_PRICE_COLOR`) - both dotted rather than dashed specifically to stay visually distinct from the order lines. Buy = red, sell = green throughout this overlay (`_BUY_COLOR`/`_SELL_COLOR` in `chart.py`) - deliberately the opposite of the candle body colors, which are about price direction, not order side. The visible y-axis is capped to a "nearby" window rather than stretching to fit every order line: any buy/sell/current-price line within 50% of the candle range of the candle high/low counts as close enough to matter (`nearby_span`), and the axis is then fit *tightly* to whatever that actually includes (candles plus qualifying lines, plus a small 3% breathing-room margin so a line doesn't sit exactly on the plot border) - not padded out to a fixed margin regardless of whether there's a line there to show. A deep DCA rung or a distant take-profit outside that window just renders off the edge instead of stretching the chart, and its "#N"/"TP"/"Now" label is explicitly skipped when off-range too (matplotlib's `text()` isn't clipped to the axes by default, so an unfiltered label would otherwise float in blank space beyond the visible chart). Fill-triangle stack/base offsets are still sized against the candle range alone, not this nearby-window content range, so stacking stays proportional to the candles regardless of how many order lines happen to qualify. The x-axis is tightened the same way: mplfinance plots candles at integer positions and adds its own ~7% left/right margin by default, so every panel's xlim is set to `(-0.5, len(df) - 0.5)` - just enough that the outermost candles aren't clipped, not the wider default gap. The "Price"/"Volume" axis labels, the volume panel's numeric y-ticks (now also a smaller panel via `panel_ratios=(6, 1)`), and the x-axis date/time tick labels are all stripped after the plot is built (`price_ax`/`volume_ax` housekeeping in `render_candles`) - deliberately kept minimal; the price y-axis numeric ticks stay, since those are the actual reference needed to read the fill/order-line overlay, not decoration. This is the same chart used everywhere (fills, `/status`, heartbeat), so the overlay is identical regardless of which message it's attached to.

`/status` and the heartbeat use `_send_status` (`main.py`), which attaches the first open position's chart as that *same* message's photo caption - one message, not a message plus a trailing photo - falling back to text-only if there's no position or the chart fails to render. `_active_coins` finds which coin(s) currently have an open position; any position beyond the first gets its own caption-less follow-up photo, since a single Telegram message can only have one photo carry a caption. `/status` sends via `update.message.reply_photo`/`reply_text` directly (bypasses the notifier/quiet-hours, same reasoning as the text-only case used to); the heartbeat uses `notifier.send`/`send_photo` so it's held during quiet hours like the rest of the heartbeat.

Every chart-bearing message - fill, `/status`, heartbeat, `/account` - passes `caption_above=True`/`show_caption_above_media=True` to `TelegramNotifier.send_photo`, so the text always renders first and the chart always lands at the bottom. Fill messages used to be the one exception (chart on top, table below, on the reasoning that the chart was "the point"); that's no longer the case - consistency of chart placement across every message won out.

### `/account`

Account-wide, not vault-specific: account equity, HYPE staked (plus its equity and current price), this depositor's equity and all-time profit in the watched vault, then PnL per period - no volume, that's `/account`'s one deliberate omission from what Hyperliquid's own Portfolio/Staking pages show. `HyperliquidClient.get_portfolio` calls the `portfolio` info endpoint for `USER_ADDRESS` (not the vault), returning value/PnL/volume history per period (`day`/`week`/`month`/`allTime`, plus `perpX` variants scoped to direct perp trading only - this account trades through the vault, so those read as ~$0 and `format_account_summary` skips them). Account equity comes from the latest point of the `day` period's `accountValueHistory` (spot + perp + every vault this address is in, combined - the same figure Hyperliquid's UI shows); staked HYPE from `get_staking_summary`'s `delegated` (not `undelegated` or pending-withdrawal, which aren't actively staked), multiplied by `get_mid_prices()["HYPE"]` for its equity (that same per-HYPE mid price is shown just below as its own "HYPE price" row); vault equity reuses `_user_equity(client.get_vault_details())`, the same figure `/status` shows. "Vault profit" right below it is `vaultDetails`' `followerState.allTimePnl` (`main.py`'s `_vault_all_time_pnl`) - this depositor's cumulative profit since joining the vault, not to be confused with the API's sibling `pnl` field (a more recent-window figure) or the "allTime" row further down in the PnL grid (that one's the whole account across every vault/spot/perp, not this one vault). Each period's % is PnL over that period's *starting* value, omitted when the start is ~0 (`allTime`, since the account began at 0). The `allTime` row also gets an unlabeled EUR-equivalent row right below it, same `eur_rate` treatment as Account equity's - only `allTime`, not Day/Week/Month, per what was asked for. Labels in the message itself all say "equity" for consistency; internal variable/API field names ("accountValueHistory" etc.) stay as Hyperliquid's own API names them.

Right after "Vault equity" comes "Earn" - the net value (supplied minus borrowed) of this address's position in Hyperliquid's lending product, across every token. `borrowLendUserState` isn't wrapped by the SDK at all, so `get_earn_value` goes straight to the raw `POST /info` (same pattern as `get_vault_details`).

Two more rows piggyback on data already fetched elsewhere in the message rather than needing their own call: "BTC price" sits right after "HYPE price" (same `get_mid_prices()` call, just also reading `["BTC"]`), and the EUR equivalent of "Account equity" sits right below it as an unlabeled row (blank label, just the €-prefixed value - `format_table` pads a blank label the same as any other, so it lines up under the $ row instead of needing its own row name), converting the same `account_value` using a live USD/EUR rate. That rate is the one genuinely external (non-Hyperliquid) data source in this bot - Hyperliquid's own "EUR" spot token is listed but has no trading pairs, so there's no price feed for it to reuse the way `get_spot_prices`/`get_earn_value` do for other tokens. `main.py`'s `_usd_to_eur_rate` hits the free, no-key-needed Frankfurter API (ECB reference rate) with a short timeout, and returns `None` on any failure rather than raising, so a forex-API hiccup just skips that one row instead of breaking `/account` - `format_account_summary` treats `eur_rate`/`btc_price` like every other optional field (omitted when `None`).

Non-dust spot balances (worth $3+) get one row each - just coin name and $ value, no separate table - appended directly after that in the same header block, sorted by value; dust is dropped so a wallet with many near-zero token balances doesn't clutter the summary. Valuing a spot token (or a lending-position token) requires resolving it by *index*, since `all_mids` only covers perps and raw `"@<index>"` pair names, not spot tokens by their own symbol, and token list *position* doesn't reliably match a token's declared `index` (the index space is sparse - hundreds of tokens with indices up into the 800s). `HyperliquidClient._token_names_and_prices` does this once (index -> name, and name -> USD price via each token's USDC-quoted spot pair in `spot_meta_and_asset_ctxs`) and is shared by both `get_spot_prices` and `get_earn_value`.

`/account` also attaches a HYPE/USDC spot chart as the message's photo (`main.py`'s `_render_spot_chart`), text above per the same `caption_above`/`show_caption_above_media` convention `/status` and the heartbeat use - falling back to text-only if the chart fails to render, same as everywhere else. It overlays this depositor's own spot buy fills as triangles (same `render_candles` treatment as a vault position's buy fills), but no resting-order lines or entry-price line - there's no vault position behind it, just this user's personal spot DCA. Getting there needs its own path rather than reusing `_render_chart`: candleSnapshot doesn't accept a spot token by its own symbol, only by its internal pair name (often a raw `"@<index>"`, e.g. HYPE/USDC is `"@107"` - `HyperliquidClient.get_spot_pair_name` resolves it, mirroring `_token_names_and_prices`' index lookup), and `_render_chart` ties one `coin` argument to both the candle-fetch identifier and the chart's title/fills/order-line filtering - which would conflate `"@107"` (fetch) with `"HYPE"` (title) here. Fills also come from a different account entirely: `HyperliquidClient.get_user_fills_since` (as opposed to `get_fills_since`, which is always scoped to the vault) hits `user_fills_by_time` for `USER_ADDRESS` directly, since a HYPE spot buy is this depositor's own trade, not the vault's.

"HYPE avg buy" (right after "HYPE price") is this depositor's weighted-average cost basis on their HYPE spot holding, factoring in both buys and sells: `state_tracker.update_cost_basis` walks fills chronologically, a buy adding to both running position and cost basis, a sell removing proportionally from cost basis (weighted-average - a sell doesn't change the average cost of what's left) and resetting both to 0 if it empties the position, so a fresh buy afterward starts a clean average rather than inheriting rounding dust from a fully-closed-out holding. This runs against this depositor's *entire* HYPE spot history, which only grows over time, so replaying it in full on every `/account` call would mean strictly increasing work for no benefit - `VaultState.hype_spot_position`/`hype_spot_cost_basis`/`hype_spot_synced_until_ms` cache the running totals in-process, and `main.py`'s `_update_hype_avg_buy_price` only fetches fills since the last call (`get_user_fills_since(state.hype_spot_synced_until_ms)`) and applies just those - full history is only ever fetched once, the first time `/account` runs after a restart (`synced_until_ms` starts at 0). This cache doesn't survive a restart (`VaultState` is in-memory only), so it gets rebuilt once, cheaply, the next time it's needed.

### `/config`

An inline-keyboard submenu (`_config_menu_markup`, `InlineKeyboardMarkup` - not the persistent reply keyboard the other buttons use, since these are one-off actions rather than something to keep on hand) offering five things: restart the bot, show the currently-monitored vault/user address (read-only, just the live `VAULT_ADDRESS`/`USER_ADDRESS` constants - no restart or persistence involved), and update either address. The two "Show" actions just edit the message with the value and redraw the same menu (`reply_markup=_config_menu_markup()` passed explicitly on every edit, rather than relying on Telegram's edit-without-`reply_markup` behavior, which isn't worth depending on here) so the menu stays usable afterward. Restart and the two updates all ultimately go through the same mechanism - persist to `.env` if applicable, then end the process so systemd starts a fresh one - because this bot has no in-process path to safely change `VAULT_ADDRESS`/`USER_ADDRESS` mid-run: `HyperliquidClient` and every piece of `VaultState` (order numbers, `first_entry_price`, the HYPE cost-basis cache, etc.) are all keyed to whichever vault/user the process started with, so hot-swapping them would mean rebuilding all of that by hand instead of just letting startup do it naturally.

**Restart mechanism.** `run()` creates an `asyncio.Event` (`shutdown_event`, stored in `bot_data` so handlers can reach it) that `poll_loop`'s `while` condition checks; its per-cycle sleep is `asyncio.wait_for(shutdown_event.wait(), timeout=POLL_INTERVAL_SECONDS)` rather than a bare `asyncio.sleep`, so setting the event wakes the loop immediately instead of waiting out the rest of the current interval. Once `poll_loop` returns, `run()`'s `finally` block shuts the `Application` down, `run()` itself returns, and `main()` - for whom a returning `run()` only ever means "a restart was requested," since there's no other path to get there - logs that explicitly (so `journalctl` shows a clear reason rather than a bare exit) and calls `sys.exit(1)`. `deploy/hl-vault-reportbot.service`'s existing `Restart=on-failure` then does the actual respawn - no code here calls `systemctl` or needs any elevated permissions to restart itself, it just exits non-zero and lets systemd's already-configured policy do the rest (the same policy the watchdog in "Hang recovery" below relies on).

**Address updates.** Tapping "Update vault/user address" sets `state.pending_config_update` to `"vault"`/`"user"` and edits the message into a prompt (with its own inline "Cancel" button). The next plain-text message from the authorized chat is caught by `handle_config_reply` (a `MessageHandler` on `filters.TEXT & ~filters.COMMAND`) - an ad-hoc pending-flag flow rather than a full `ConversationHandler`, since this bot only ever talks to one chat and doesn't need general multi-step conversation tracking. It's validated against `_ADDRESS_RE` (`0x` + 40 hex chars) before anything is written - a rejected address leaves the pending flag set so the user can just retry - then persisted with `dotenv.set_key(find_dotenv(), "VAULT_ADDRESS"/"USER_ADDRESS", address)`, which rewrites just that one line and leaves the rest of `.env` untouched, before the same restart mechanism kicks in. Handler is a no-op whenever nothing is pending, so it doesn't interfere with any other message in the chat.

**Authorization.** `CommandHandler("config", ...)` is scoped with `filters.Chat(int(TELEGRAM_CHAT_ID))` like every other command, and the `MessageHandler` above adds the same filter directly - but `CallbackQueryHandler` (button taps) has no `filters=` parameter to do this at registration time, so `handle_config_callback` and `handle_config_reply` both also check `_is_authorized(update)` (comparing `update.effective_chat.id`) themselves as a second layer, since a callback query's chat isn't filterable the same way a message's is.

### Money math conventions

- "Exposure" / notional figures are relative to the **whole vault** (`vault_value` from margin summary).
- Dollar PnL and equity are **scaled to this depositor's share** (`equity / vault_value`, called `fraction` in `state_tracker.py`), since the vault pools multiple followers' capital.
- `format_open_orders` shows both: "Exposure" follows the first rule (whole-vault %), "Value" is the exception - scaled to `fraction` like PnL/equity, since what matters there is what a resting order is actually worth to this depositor if it fills. A "Total" footer row sums both across every order. No "Side" column - every row is a buy (sells are shown via `format_position_status`'s "Sell price" row instead); a reduce-only buy is distinguishable only by having no rung number in "#", since `assign_order_numbers` doesn't number those.
- Telegram's `<pre>` blocks can't render bold text inline, so `format_table`/`format_grid` use fixed-width padding for alignment instead of markdown emphasis.

### Hang recovery

The event loop has previously frozen for hours with no crash or log output, because two lower-level clients had no bounded timeouts: the Hyperliquid SDK's `requests` session (synchronous, blocks the whole loop) and python-telegram-bot's own connection pool (observed getting stuck in `CLOSE_WAIT`, wedging both outgoing sends and the `/status` polling loop, since they share one `Bot`/connection pool). Three layers now guard against this recurring silently:

1. `HyperliquidClient` sets `REQUEST_TIMEOUT_SECONDS` (`src/hl_client.py`) on the SDK's session.
2. `TelegramNotifier.send` wraps the send in `asyncio.wait_for(..., SEND_TIMEOUT_SECONDS)` (`src/notifier.py`) as a backstop above the Bot's own per-request timeouts, since those didn't prevent the observed hang.
3. `main.py`'s `_sd_notify` kicks the systemd watchdog (`WATCHDOG=1`) once per completed poll cycle; `deploy/hl-vault-reportbot.service` sets `Type=notify` and `WatchdogSec=240`, so if a cycle ever truly hangs (no kick), systemd force-restarts the process. This is the layer that recovers even from hangs the two timeouts above don't anticipate, since a full process restart is the only way to fully reset the network client's internal state.
